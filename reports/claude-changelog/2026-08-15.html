◆ A behavior change you did not ask for

Breaking 2.1.233

Todo and task-tracking tools are off on Opus 4.8, Sonnet 5, Fable 5, Mythos 5 and newer

The changelog states it plainly: TaskCreate, TaskGet, TaskUpdate, TaskList and TodoWrite are no longer available on those models, and CLAUDE_CODE_ENABLE_TODO_TOOLS=1 restores them. No reasoning is given in the entry, so treat the stated scope as the whole story rather than guessing at intent.

The practical shape of this: on a current model, a long task will no longer emit a visible checklist unless you opt back in. Anything downstream that parsed or displayed that checklist sees nothing.

So what for TSD: Check your scheduled tasks and any skill whose instructions say "track progress with TodoWrite" or "create a task per item" — those lines are now dead text on your default model. Two options. Leave it off and let the agent work without the ceremony, which is the intended default and one less tool call per step. Or, if you rely on the checklist to watch a long unattended run, export CLAUDE_CODE_ENABLE_TODO_TOOLS=1 in the environment that launches those jobs. Pick one and make it consistent, because half your skills assuming the tools exist while the model cannot call them is the worst of both.
Claude Code changelog — 2.1.233
Fix 2.1.233

Notification hooks were not firing for permission prompts in Desktop and VS Code

Permission prompts failed to trigger Notification hooks when running under Claude Desktop or VS Code. Separately, cloud sessions were sometimes marked as lost when the environment shut down while Claude sat waiting on a permission prompt.

Both failures share a cause pattern: a blocked session looked idle to the layer above it.

So what for TSD: If you ever wired a Notification hook to ping you when a run stops for approval and concluded it did not work, retest it in the desktop app. A run that blocks on approval and never tells you is the single most expensive failure mode in an unattended job — you lose the whole window, not the step. The cloud-session fix matters the same way for anything you kick off and walk away from.

◆ Skills and plugins got less brittle

Fix 2.1.233

Shadowed bundled skills reported "Unknown command" in headless runs

Bundled skill aliases such as /checkup and /review reported "Unknown command" in -p mode, or with plugins and MCP loaded, when a user or project skill shadowed the bundled skill. Alongside it, claude plugin validate now inspects a bare .claude/skills directory and reports SKILL.md files whose frontmatter fails to parse.

The shadowing bug only bit setups with a deep skill and plugin stack. That is a description of your machine.

So what for TSD: You run dozens of skills across the Vercel, Codex and anthropic-skills plugin sets plus your own, and your scheduled tasks all run headless. This is the class of bug that makes a nightly job fail with an error that reproduces nowhere interactively. Worth a pass: run claude plugin validate against your skills directory now that it checks bare .claude/skills, and you will find any SKILL.md whose frontmatter has been quietly unparseable.
Claude Code changelog — 2.1.233
Fix 2.1.233

Skill argument values were being re-expanded as template markers

Skill and command argument substitution was fixed to prevent argument values from being re-expanded as template markers. In other words: pass an argument whose text happens to look like the template syntax, and it got substituted a second time on the way through.

So what for TSD: This hits any skill you invoke with free-form text — a prospect name into a sales skill, a client brief into a build skill, a raw draft into the-humanizer. The failure was silent corruption of the argument rather than a crash, so nothing in your logs would have flagged it. No action needed beyond updating, but if you ever saw a skill mangle an argument and wrote it off as model weirdness, that was probably this.
Claude Code changelog — 2.1.233

◆ Connections: MCP servers and WebFetch

Fix 2.1.233

MCP v2 stopped endlessly reopening streams against serverless hosts

MCP v2 connections were endlessly reopening the subscriptions/listen stream against servers that terminate long-held streams on a fixed timeout — the changelog names serverless hosts as the example.

A reconnect loop against a hosted server is not a cosmetic problem. It is request volume you are paying for and log noise you have to read past.

So what for TSD: Most of your MCP surface is hosted and remote — Supabase, Notion, Calendly, Vapi, the Higgsfield server. Any of them that cuts idle streams on a timer was in this loop. Update and watch whether your session startup and idle behavior gets quieter. If a specific connector has been flaky in a way you never fully diagnosed, retry it before assuming the server is the problem.
Claude Code changelog — 2.1.233
New 2.1.233

WebFetch cache TTL is now configurable, and print mode names unrecognized models

Two knobs for automated runs. CLAUDE_CODE_WEBFETCH_CACHE_TTL_MS configures the WebFetch session URL cache TTL, with the default unchanged at 15 minutes. And in print mode, a [claude-code:unrecognized_model] line goes to stderr when a request goes out for a model ID Claude Code does not recognize, which you silence by mapping it with modelOverrides.

So what for TSD: The TTL knob is for exactly the jobs you already run — this scout routine, and anything that scrapes a client's site or a docs page more than once in a session. Drop the TTL when a run needs to see a page change within the same session; raise it when you are hitting the same URL repeatedly and want the fetch to cost nothing. The stderr diagnostic is the more useful of the two: pin it in your scheduled-task logs and a typo'd or retired model ID surfaces as a line you can grep instead of a run that quietly behaves wrong.
