◆ Unattended runs get more honest about failure

Fix 2.1.269

/goal retries instead of dying quietly

A goal run that hit an API error, a network drop, or a token limit used to just stall with nothing telling you why. It now retries with backoff, or pauses and states the reason out loud — including waiting out a usage-limit reset. A related fix: remote and headless sessions were reporting "waiting for your input" while a background agent was still working; that's now accurate.

So what for TSD: This routine you're reading right now runs unattended overnight via Nash OS. A silent stall used to mean you'd find out the next morning that nothing shipped, with no error to point at. Same logic applies to any scheduled or headless job you build for a client — a retry-with-reason beats a dead session.
Changelog · 2.1.269
Fix 2.1.269

Prompt cache stops silently invalidating on resume

Two fixes: a response cut off at the output-token limit and auto-resumed was partially invalidating the prompt cache on the next turn, and resuming a session after interrupting Claude mid-thought could change how earlier context got re-sent — also hurting cache reuse. Separately, sessions that got permanently stuck on "Prompt is too long" during auto-compaction (mostly Agent SDK sessions with very large prompts, when there was no complete earlier exchange to summarize) are fixed.

So what for TSD: You pay by the token. Interrupting Claude mid-answer to redirect it is a normal move in a long build session — it shouldn't quietly cost you a full cache rebuild on the next message. If you're building anything on the Agent SDK with large prompts, the compaction stuck-state fix removes a real dead end.

◆ Bigger fan-outs, auditable Bash

New 2.1.269

Workflow tool concurrency cap raised to 256

CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS (1–256) raises the Workflow tool's per-run concurrent-agent limit, aimed at fan-outs that are bound by inference wait time rather than local CPU.

So what for TSD: The default cap is already ~10 concurrent agents per workflow, which covers almost anything you'd run for a single client. This matters only if you build a workflow that genuinely needs a much wider fan-out — a bulk content migration across dozens of pages, say — where the bottleneck is waiting on model responses, not your machine.
Changelog · 2.1.269
New 2.1.269

Bash tool can attach a diff of what it edited

New setting bashEditDiffEnabled: when a Bash command edits a file, the tool result now includes a diff of the change, matching what the Edit and Write tools already show.

So what for TSD: A lot of agent-driven file edits on your projects happen via sed/awk-style Bash one-liners rather than the Edit tool, and those were previously a black box in the transcript — you'd have to go check git diff yourself. Turning this on gives you the same in-line accountability for Bash edits as for everything else, worth flipping on for client repos.

◆ Client repo hygiene

Fix 2.1.269

A CLAUDE.md "no attribution" rule now actually wins

The built-in attribution reminder was overriding a CLAUDE.md or memory rule that told Claude not to attribute commits or pull requests to itself. That's fixed — the project-level rule now takes precedence. Lines set by managed settings still apply on top.

So what for TSD: If any Bisque, Studio C, or Sonderwerks repo has a CLAUDE.md rule against "Co-Authored-By: Claude" on commits, it was quietly being ignored before this fix. Worth a spot-check on recent commit history for those repos to confirm the rule is actually holding now — and a good reason to add the rule anywhere you haven't yet.

◆ VS Code: watching sub-agents without leaving the editor

New 2.1.269

Agent map, Hooks dialog, and Permission rules dialog

Three additions: an "N agents" footer pill opens a map of a session's sub-agents with per-agent cards, a Stop agent control, and read-only transcripts; a Hooks dialog in the command menu lists hooks and lets you add, edit, or remove them across user/project/local settings; and a Permission rules dialog does the same for permission rules. Managed, plugin, session-only, and startup-option entries stay read-only in both.

So what for TSD: If you run multi-agent workflows or teams inside the VS Code extension, you get a way to see and kill a runaway sub-agent without dropping to the terminal, and to fix a permission rule mid-session instead of editing settings.json by hand. Small, but it closes the gap between the terminal and VS Code workflows.
