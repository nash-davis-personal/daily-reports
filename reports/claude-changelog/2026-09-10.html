◆ The prompt-cache repair wave

Fix 2.1.267

Ten separate paths were rewriting the tool block mid-conversation

This is the bulk of the release. Each of these independently broke prompt-cache reuse, and several also dropped earlier extended thinking: an MCP server re-sending a tool the model already loaded; a tool vanishing mid-conversation from a disconnected server or an upgrade; a background worker forked from a conversation injecting EnterWorktree into the tool block; mid-session MCP and plugin tools being appended in sessions without ToolSearch (supported models now get them as deferred definitions); /model re-sending every tool definition on a switch.

The resume-specific half is just as long: resumed sessions rewriting the inline tool set when an MCP connector reconnects at a different moment, re-rendering tool descriptions instead of replaying recorded ones, rewriting earlier MCP tool announcements before connectors reconnect, and a cache break when a print-mode conversation is resumed interactively. Separately, subagents and sessions started with --system-prompt or --append-system-prompt now record the system prompt and tool definitions once instead of re-rendering them.

So what for TSD: You run a lot of MCP servers — supabase, vercel, notion, nash-os, tsd-portal — and they reconnect at unpredictable moments. Every one of those reconnects has been costing you a full cache miss on long client sessions, which is real money on Bisque and Sonderwerks builds and is why resumed sessions sometimes felt dumber than the originals. Upgrade past 2.1.247 before the next long build session.
Changelog · 2.1.267
Fix 2.1.267

Large and scripted sessions reload cleanly

Two resume bugs that hit automation specifically. Resuming after /compact or another slash command ran via -p --resume no longer inserts a spurious "Continue from where you left off." turn. And resuming a transcript over 5 MB no longer drops parallel tool calls and their hook output from the reloaded conversation. --resume first-render time also improved for sessions with many Bash calls.

So what for TSD: Your scheduled tasks are print-mode runs. The phantom turn was polluting the very context those runs depend on, and the 5 MB drop means any long-running steward loop was resuming with holes in its history. If a scheduled task has been producing slightly-off output, this is a plausible cause worth ruling in.

◆ Effort, cost, and prompt iteration

New 2.1.267

maxEffortLevel puts a ceiling on every provider

A new setting placed either top-level or per model under modelSettings. It caps the effort level on every provider, including Bedrock, Vertex and Foundry. Users can still choose something lower than the cap; they just cannot go above it.

So what for TSD: This is the knob for unattended work. Cap the effort on your scheduled tasks and steward loops — the daily changelog scout, the loose-ends sweep — where a high effort level buys nothing, and leave your interactive delivery sessions uncapped. It is a settings change, so it costs you one edit and pays out every night.

Fix 2.1.267

effort: frontmatter was silently ignored on three models

effort: frontmatter on custom commands, skills, and subagents was being dropped on models whose default effort is still pinned — Opus 4.7, Opus 4.8, and Fable 5. It now applies.

So what for TSD: You have a large custom skill library — the advisor skills, sales-psychology, the-humanizer, loop-engineering. Any effort: you set in those was doing nothing on those three models. Worth re-reading your frontmatter now that it is load-bearing, because the levels you wrote are about to actually take effect.
Changelog · 2.1.267
New 2.1.267

--system-prompt-snapshot off for prompt iteration

Renders the system prompt fresh on every request instead of reusing the conversation's recorded prompt. Built for iterating on prompt text — it deliberately gives up the caching behavior the rest of this release works to protect.

So what for TSD: Useful when you are tuning a skill's system prompt and want each edit to land without restarting the session. Turn it back off before doing real work, since it defeats the snapshot the cache relies on.

◆ Security, plugins, and the surfaces you deploy from

Security 2.1.267

Marketplace containment bypass, and managed settings now fail closed

A marketplace entry path containing a backslash could bypass the containment check for fetched marketplaces on macOS and Linux. Alongside it, managed allowedHttpHookUrls, httpHookAllowedEnvVars and allowedChannelPlugins were fixed to admit nothing when unreadable, rather than everything.

So what for TSD: You install plugins from marketplaces — vercel, codex, anthropic-skills. The containment bypass is the kind of thing that turns a third-party marketplace into a path-traversal vector on your delivery machine. Straight upgrade reason on its own.
Changelog · 2.1.267
Fix 2.1.267

Claude Code on the web stops failing gh calls in orgs without the GitHub App

gh and GitHub API calls in organizations without the Claude GitHub App installed now fall back to your connected GitHub account, and say so explicitly when no account is connected. GitHub Enterprise Server sessions also refresh an expired token automatically instead of reporting the account as disconnected.

So what for TSD: Relevant if you push client work from the web client. The bisqueimports repos sit under a team you are a member of rather than one you own, so the no-App fallback path is exactly your situation. It failing quietly is worse than it failing loudly, and now it tells you.
Changelog · 2.1.267
Improve 2.1.267

Artifact publishing retries a dropped upload, and explains refusals

Publishes cut off by a dropped connection mid-upload now retry once when Claude Code can tell the upload never completed, instead of reporting an unknown outcome. Refused publishes now say why and what to do. Publishing a page file that isn't valid UTF-8 or contains a replacement character now names the line and column.

So what for TSD: Artifacts are how you hand clients a preview without standing up a deployment. "Unknown outcome" on a dropped upload meant re-publishing and hoping you hadn't made two. That ambiguity is gone.
