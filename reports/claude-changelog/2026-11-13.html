Claude Code Changelog ◆Friday, November 13, 2026 ◆One release: 2.1.323

2.1.323 lands: Code Mode, a 100,000-message cap between sessions, and tighter permission rules

One release since yesterday's briefing, and it is a large one: 2.1.323, dated November 12, with 27 additions, 51 changes, 21 improvements and 195 bug fixes. The parts that touch your setup are the automation ones: sessions can message each other far more freely, permission rules got stricter in ways that can stall an unattended run, and scheduled tasks and Remote Control each got real fixes.

◆ Agents and automation

New 2.1.323

Code Mode: Claude writes JavaScript to call its tools

The entry reads: an experimental opt-in in which Claude writes JavaScript to call its tools, with a pointer to code.claude.com/docs/en/code-mode for turning it on, or turning it off for an organization. That is the whole description in the changelog.

The docs page returned 404 when this briefing was filed, so the switch that enables it and any limits are unconfirmed here. Nothing in the source says what it costs or saves in tokens or time.

So what for TSD: Leave it off on client repos (Bisque, Studio C, Sonderwerks) while it is labeled experimental. Once the docs page loads, try it in one tool-heavy personal session, the kind with a dozen MCP servers connected, and compare a real task with it on and off before deciding anything.
Changelog: 2.1.323, Added
Change 2.1.323

Sessions can send each other up to 100,000 messages without you

Two matching lines. Each of your sessions on the same machine could send the others about 20 messages without a prompt from you; that is now 100,000. A Claude Desktop Code tab session had the same limit of 20 before it waited for you to type again; that is also 100,000 now.

Related in the same release: workflows in the desktop app's Code tab now pause at a usage limit and continue after it resets, a finished subagent's transcript is freed from memory sooner, and hooks that run long in claude -p and SDK sessions send a progress heartbeat every 30 seconds so a host does not end the turn as hung (the changelog says that takes effect once Claude Desktop includes this version).

So what for TSD: Any setup where one session hands work to another (a producer session and a review session on the Production Line, Nash OS dispatching jobs) will no longer stop at message 20 waiting on you. The old cap also worked as a brake. Two sessions that loop on each other can now burn through a usage limit unattended, so give long hand-off chains an explicit stop condition.
Changelog: 2.1.323, Changed
Fix 2.1.323

Scheduled tasks that silently skipped a run

Fixed: scheduled tasks from an ended session sometimes not running after another session in the same folder used /clear, /resume or /branch. Also fixed for unattended runs: claude -p silently using another model when settings block the requested one (it now warns on stderr), and claude -p and the Agent SDK running Bash unsandboxed when sandbox settings failed validation (start-up now stops and names the bad setting).

On the web side, a scheduled task whose run cannot start because its settings need an unavailable sandbox now sends a failure notification, and removing a repository from a scheduled task no longer moves its GitHub trigger to a different repository.

So what for TSD: This briefing series has no files for November 7 through 10. The changelog cannot say whether this bug caused that, but it fits the symptom: a task that just does not fire. After updating, check the run log on the Nash OS Machine page for a week and see whether the daily tasks stop missing days.

◆ Permissions, sandbox and MCP

Behavior change 2.1.323

Wildcard Bash rules now ask more often, and the sandbox blocks more

Allow rules with an attached wildcard such as Bash(ls*) skipped the prompt in some cases; that is fixed, and a rule that names a variable such as Bash(NODE_ENV*) now asks. Start-up warns about allow rules with a * in a variable's value, like Bash(PORT=* npm run dev). Deny and ask rules now catch commands run through sudo, env and similar wrappers. A "don't ask again" rule that looks like it holds a secret, or would land in a settings.local.json that git tracks, lasts for the session only.

In the sandbox on macOS and Linux, git worktree add, move and remove now fail read-only, as do commits in a worktree the session was not started in or given. Write access granted through a symlink that leads elsewhere is ignored. And --permission-mode auto or defaultMode: auto now starts in Manual mode when auto mode is unavailable, where before it could start in a mode that allowed more.

So what for TSD: These are security fixes and they are worth having on machines that hold client credentials. The cost is that a scheduled or background run which relied on a loose rule will now sit at a prompt nobody answers. After updating, start one interactive session in each repo you automate, read any start-up warning about allow rules, and rewrite the flagged rules as exact commands.
Changelog: 2.1.323, Changed and bug fixes
Behavior change 2.1.323

MCP: sign-in always confirms, approvals match exact names, v1 client removed

The tool Claude uses to finish an MCP server sign-in now asks you to confirm, even in bypass and auto modes; where nobody can be asked, such as dontAsk mode, the changelog says to use /mcp. Project .mcp.json server approvals now match the server's exact name, so an approval written in another spelling asks again. The v1 MCP client is removed; MCP_SDK_GENERATION=v1 now runs the v2 client in a compatibility mode.

Smaller MCP items: /mcp shows how many of a server's tools were left out because the API would reject their input schema, MCP tool calls that hit an expired token now ask you to sign in again where they used to end in TOKEN_EXPIRED, and a server that needs authentication opens on "Reconnect" in /mcp.

So what for TSD: An unattended run can no longer complete an MCP login by itself. Before relying on a connector in a scheduled task (Supabase, Vercel, Stripe, the Higgsfield servers), open /mcp in a live session and sign in there. If a project server suddenly asks for approval again after the update, the name in your approval entry differs from the one in .mcp.json; approve it once and move on.

◆ Working from the phone and usage limits

Fix 2.1.323

Remote Control: nine fixes to connection state and what the phone shows

Sessions no longer show as disconnected for a minute or more after switching Wi-Fi or reconnecting a VPN. claude remote-control restarted in the same folder more than 4 hours after it stopped used to reconnect as a new computer; it now keeps its identity for up to 30 days. Desktop app sessions no longer show as idle on the phone while background subagents are still running.

Three fixes are about prompts you could not see: the usage-credits question now also shows in the Claude app, a session waiting on a terminal-only permission prompt no longer reads as running, and phone notifications now say what Claude is asking permission for when DISABLE_TELEMETRY or DO_NOT_TRACK is set. There is also a Try again button on the error shown when the host computer is signed out.

So what for TSD: You answer decisions from your phone, so a session that looks "running" while it waits on a hidden prompt is lost time. Update both Macs and restart claude remote-control on each so the 30-day identity fix applies. If a session still looks stuck from the phone after this, it is more likely a real terminal-only prompt.
Changelog: 2.1.323, bug fixes
Improve 2.1.323

Fable limit and usage-credit messages now say when and what next

When a model needs usage credits that are off or used up, there is now an options menu: stop, switch to usage credits, or upgrade. Fable's weekly limit showed no reset time and no options menu in the terminal; fixed. The Fable limit message in -p, SDK, IDE and cloud sessions now says when the limit resets and how to continue. /usage keeps the session and weekly bars for setup tokens and CLAUDE_CODE_OAUTH_TOKEN.

So what for TSD: When a long build session hits the weekly Fable limit mid-task you will now see the reset time and can choose on the spot between waiting, paying, or dropping to another model. Decide ahead of time which client work is worth usage credits so the menu is a ten-second call.
