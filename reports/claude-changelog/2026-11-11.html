Claude Code Changelog ◆Wednesday, November 11, 2026 ◆2.1.319, 2.1.321 and 2.1.322

Fable 5.2 becomes the default model and headless runs can deny a permission prompt and keep going

The quiet window ended the same day the last briefing filed: 2.1.319 landed on November 6, then 2.1.321 on November 9 and 2.1.322 on November 10. Together they change which model your builds run on, give scheduled and headless sessions a way past permission prompts, move long MCP tool calls to the background, and close four security holes.

◆ Models and cost

New 2.1.321

Claude Fable 5.2 ships as the default Fable model with 1M context

The changelog lists Claude Fable 5.2 (claude-fable-5-2) at 1M context and $8/$40 per Mtok with $0.20/Mtok cache reads. Saved Fable 5.1 model picks move to the fable alias at once on Pro and Max plans, and on Team and Enterprise once the organization allows it. /model claude-fable-5-1 switches back.

Two related changes: the fast mode labels in /fast, /config and /model now name your current model when it supports fast mode, and a fix stops fast mode from losing replies or switching models when fast serving is rate-limited; it now tries standard speed on the same model first.

So what for TSD: Every session since Nov 9 has been on a different model than the one that built the Bisque, Studio C and Sonderwerks sites. Run one real task on each active project this week and read the output with that in mind. If a workflow regresses, pin 5.1 with the slash command above and note it in the command vault rather than guessing which model did what.

◆ Unattended and scheduled runs

New 2.1.319

A tool call that would prompt can now be denied so the turn continues

The new permissions.denyInsteadOfPrompting setting denies any tool call that would otherwise wait on a permission prompt, in terminal sessions, subagents and teammates. In the same release, claude -p in auto mode now exits 1 in text and JSON output when its actions were refused because no safety check was available, where it used to exit 0.

2.1.321 adds a related relief: the account email check now refuses only a shell command that holds your email and names a User-Agent, and does so without asking, so other commands and scheduled runs no longer stop at that prompt.

So what for TSD: This is the fix for scouts and overnight jobs that die waiting on a prompt nobody will answer. Turn the setting on for every scheduled task that runs headless, and treat a non-zero exit from claude -p as the signal that a run was refused rather than silently successful. Check the Nash OS run log for any job that has been reporting success with no output.
Changelog · 2.1.319 and 2.1.321
Change 2.1.319

Self-paced /loop stops when a turn ends without rescheduling

A self-paced /loop used to schedule a fallback wakeup when a turn finished without rescheduling itself. It now ends. CLAUDE_CODE_LOOP_KEEPALIVE=1 restores the old behavior. Cloud sessions also get a note on /loop confirmations that a timer stops with its container, with an offer of a loop that survives.

So what for TSD: Any watcher loop you lean on (a deploy poll, a TSDPL review wait) will now quietly end if one turn forgets to reschedule. Either set the keepalive variable in the environment that runs them or make the loop prompt explicit about rescheduling every turn.
Changelog · 2.1.319
New 2.1.321

Remote Control applies one settings file to every session and stays put

claude remote-control --settings <file> applies a settings file to every session it starts; if the file changes, no new session starts until you restart claude remote-control. Remote Control sessions now keep the folder they were started in, so a connected client can no longer move a session to another folder. 2.1.319 also makes claude remote-control exit 1 with a reason when a first-run question gets no answer, instead of exiting silently with 0.

So what for TSD: Your phone-driven sessions can carry one permissions file for the whole day. Keep that file under version control next to the launchd plist, and expect any script that starts remote-control to need its first-run answer piped in, since the silent exit is gone.

◆ Agents, MCP and tools

New 2.1.319

MCP tasks move to the background right away in the terminal

When an MCP server runs a tool call as a task, Claude Code now backgrounds it immediately and tells Claude the result when it finishes. CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND makes Claude Code wait inside the tool call instead, and CLAUDE_CODE_DISABLE_MCP_TASKS=1 turns tasks off entirely. The feature works without feature-flag fetching, so it also runs on Bedrock, Vertex, Foundry and LLM gateways.

Also in this area: a /tasks row called "Earlier in this session" lists finished subagents so you can reopen and message one after it leaves the list or you restart, and 2.1.321 answers reports from background subagents that wait together in one model call in headless, desktop and VS Code sessions, as the terminal already did.

So what for TSD: Video generation and review calls on the commercial pipeline (Higgsfield takes, Gemini reviews) are the obvious beneficiaries, but only if those servers run the call as a task. Check whether the MCP servers you depend on advertise task support before assuming the session will keep moving; if a long call still blocks, the server is the reason.
Changelog · 2.1.319 and 2.1.321
Fix 2.1.321

Parallel Bash calls no longer run in the wrong folder

2.1.321 fixes Bash commands sometimes running in the wrong folder when Claude sent several at once and an earlier one changed folders. 2.1.319 fixes background Bash commands that finished almost instantly losing their output while being reported as completed, and the Bash tool's diff of changed files missing a file the command wrote just before it ended.

So what for TSD: If a build step ever ran against the wrong repo during a multi-project session, this was a plausible cause. No action beyond updating, but it removes one reason to keep each client in its own session.

◆ Security fixes

Security 2.1.319 and 2.1.321

MCP OAuth secrets, a worktree sandbox escape and two Bash permission holes

2.1.321 fixes MCP OAuth requests sending secrets such as refresh tokens to another host when a server redirected them, a case where a read-only Bash command ran outside the sandbox without a permission prompt, and Bash permission checks judging a file write from the wrong folder. 2.1.319 fixes a sandbox escape when creating a worktree, a Bash permission bypass where a crafted environment prefix could hide part of a command from permission checks, and a case where a sed command could skip the permission check in accept-edits and auto mode.

So what for TSD: You run a long list of third-party MCP servers (Notion, Vercel, Supabase, Higgsfield, Calendly, Gmail) with OAuth tokens behind them. Update every machine today, and rotate the refresh tokens on any server that has ever redirected you during sign-in. Not a maybe.
