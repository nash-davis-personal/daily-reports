◆ Agent & worktree isolation — the safety layer under your loops

Fix 2.1.210

Worktree-isolated subagents were running git-mutating commands on the main repo

The whole point of isolation: 'worktree' is that an agent works on a throwaway copy and cannot touch your real branch. This release fixes a case where those subagents could run git-mutating commands against the main checkout instead of their own worktree — the exact failure mode that turns a "safe, isolated" loop into one that quietly rewrites live state.

So what for TSD: Your Fleet Steward-style loops run in worktrees precisely so an unattended fix can't corrupt the working branch. Update to 2.1.210 before the next scheduled run — this closes the one hole that made that promise leaky.
Claude Code Changelog · 2.1.210
Fix 2.1.210

Killed background sessions left permanent worktree locks behind

When a background session got killed mid-run, it could leave a git worktree lock that never cleared, blocking future worktree operations until you found and deleted it by hand. The periodic sweep now releases locks whose owning process is gone.

So what for TSD: One less way for a scheduled loop to wedge itself overnight and greet you with a stuck queue in the morning. If you've been manually clearing lock files, that chore is gone.
Claude Code Changelog · 2.1.210
Fix 2.1.210

Agent tool hardened against injection; ultracode stops firing on non-human input

Two related hardening changes. The Agent tool is now hardened against indirect prompt injection through content a subagent reads — a page, a doc, a comment that tries to issue instructions. Separately, the ultracode keyword opt-in no longer triggers on non-human-originated input like webhook payloads and relayed PR comments, so external content can't kick off an expensive multi-agent run on its own.

So what for TSD: Your agents read client-supplied and web content constantly. This is the difference between "an agent summarized a sketchy page" and "an agent followed a sketchy page's instructions." Take it, and keep treating anything an agent reads as data, never commands.
Claude Code Changelog · 2.1.210
Fix 2.1.210

The model no longer assumes a backgrounded cd took effect

When a command containing a cd got moved to the background, Claude used to assume the directory change had landed. The tool result now states plainly that the working directory is unchanged, so the model stops issuing follow-up commands against a path it never actually moved into.

So what for TSD: Fewer silent wrong-directory mistakes in multi-repo sessions. Small, but it's the kind of bug that produces confidently-wrong output in an unattended run.

◆ Unattended & background reliability

Fix 2.1.210

Hook timeouts were misread as user rejections, stalling unattended sessions

A hook callback that timed out was being reported to the model as if the user had rejected the action. In an interactive session that's a shrug; in an unattended one it made the session stop and wait for input that was never coming. Fixed so a timeout reads as a timeout.

So what for TSD: This is the failure mode for scheduled work like this very briefing job — a slow hook could silently park the whole run. If you've seen loops mysteriously "finish" having done nothing, this is a prime suspect.
Claude Code Changelog · 2.1.210
Fix 2.1.210

claude attach stops failing during session transitions; --effort ultracode reaches dispatched sessions

claude attach was throwing "job not found" or "agent is still starting" while a session was in transition — it now waits for the daemon to settle, and a terminal resize during a slow attach is applied once it completes. Separately, claude agents --effort ultracode was silently dropping that value before it reached the dispatched session; it now carries through.

So what for TSD: If you drive background agents from the CLI, attaching is less flaky and the effort level you set is the effort level you get. Worth confirming your dispatch scripts were not quietly running at default effort.
Claude Code Changelog · 2.1.210
Improve 2.1.210

Auto mode pins Sonnet 5 as the permission classifier for external sessions

Auto mode's permission classifier now defaults to Sonnet 5 for external sessions, validated on the session's first request and pinned for the rest of that session so the decision-maker doesn't drift mid-run.

So what for TSD: More predictable auto-mode behavior if you lean on it for hands-off runs. Still verify the permission rules themselves — a consistent classifier only helps if it's classifying against the right allow/deny set.

◆ Authoring, charts & day-to-day correctness

Improve 2.1.210

dataviz skill validates chart colors with perceptual OKLab difference

The bundled dataviz skill now checks palettes using perceptual OKLab color difference and recalibrated color-blindness thresholds, so "these series are distinguishable" is judged the way an eye actually sees it, not by raw RGB distance.

So what for TSD: Directly useful for the client dashboards you ship — Bisque, Studio C, Sonderwerks all get charts. Better palette validation means fewer "these two lines look identical" complaints, including from color-blind viewers.
Claude Code Changelog · 2.1.210
Improve 2.1.210

Memory writes error loudly when MEMORY.md blows past its read limit

A memory write that would leave MEMORY.md over its read limit now produces an explicit error instead of silently truncating the index. On the same theme, unmatched $1/$2 positional placeholders in skills and commands are now preserved verbatim rather than being silently stripped.

So what for TSD: You run a file-based memory index. Silent truncation there is the worst kind of bug — it loses context without telling you. An explicit error means you find out while you can still fix it.
Claude Code Changelog · 2.1.210
Improve 2.1.210

Startup now warns on Write(path), NotebookEdit(path), Glob(path) permission rules

Claude Code now flags those path-scoped permission rules at startup and points you at Edit(path) or Read(path) instead — the forms that actually behave the way most people intend when they scope a rule to a path.

So what for TSD: If your settings.json has any of those three, expect a nudge on next launch. Cheap chance to clean up permission rules that may not be matching what you think they match.
