◆ Permission rules: gaps closed

Fix v2.1.289

Two ways past Bash deny/ask rules under sandbox auto-allow are closed

When the sandbox auto-allows commands, a deny or ask rule could miss a command that had an environment-variable prefix with an expanded value — the changelog's own example is TZ="$HOME" rm -rf build — or a bare variable assignment in front of it. Both now match. Separately, on managed machines, a deny/ask rule on a nested part of a compound shell command now holds even when a user-installed mod approved it.

So what for TSD: Your unattended scout and hub jobs are exactly the sessions where a deny rule is the only guardrail. Update to 2.1.289 on the Mac running Nash OS, then re-check that your rm/git push --force/supabase db reset deny rules actually fire on a prefixed form like FOO=1 rm -rf x.
Changelog · 2.1.289
Fix v2.1.289

Read deny rules now apply to symlinked files from the IDE

Files that were @-mentioned, changed, or selected in the IDE through a symlink weren't checked against Read deny rules. They are now. Also closed: a user-installed plugin could rewrite the descriptions of an organization-managed MCP server's sign-in tools.

So what for TSD: If any client repo symlinks a shared .env or credentials folder (common in monorepo-ish Vercel setups), your Read(.env*) deny rule was leaky in VS Code until this release. No action beyond updating; worth knowing if you ever told a client their secrets were fenced off.

◆ Plugins & agents

Fix v2.1.289

Plugin and mod faults are contained instead of ending the session

Several fixes in one direction: supervised and background sessions no longer end when a plugin's on-screen handler throws asynchronously; a bad value from a mod's ui.render hook no longer causes an "unrecoverable interface error"; a mod's Client that fails while drawn now fails alone and raises ui.fault; zero-height plugin regions and unknown Box border styles no longer crash or freeze the session. Installed mods also now load in the first session after an upgrade.

So what for TSD: This pairs with yesterday's stalled-stream fix — background runs are less likely to die from something unrelated to the task. If a scheduled job silently stopped in the last week and you have UI plugins installed, this is a likely culprit; update and let it run before debugging further.
Changelog · 2.1.289
Feature v2.1.289

agent.spawn for teammates, stable agent ids, idle/waiting states

The only additive item in the release: agent.spawn for teammates, one agent id carried across plugin hook events, and idle and waiting states exposed in $.agent.list(). The changelog gives no further detail.

So what for TSD: A stable agent id across hooks means a plugin can track one teammate from spawn to finish, which is what you'd need to build a "build / review / deploy" crew that reports status. Low priority for client work this week; bookmark it if you get to automating the Bisque or Sonderwerks build pipelines with teammates.
