◆ Locking down what the agent can touch

Fix 2.1.248

/ultrareview and cloud sessions were uploading uncommitted secret files

The changelog is specific about what leaked: /ultrareview and locally seeded cloud sessions were uploading uncommitted edits to prod.env-style and *.tfvars files, and to editor swap, temp, and backup copies of credential files — the examples given are key.pem.tmp and id_rsa.swo. Those files now stay on your machine.

The exposure window is any cloud review run on a dirty tree before you upgrade to 2.1.248.

So what for TSD: Every client checkout you run reviews in — Bisque, Studio C, Sonderwerks — has local env files holding Supabase service keys and Vercel tokens, and they are frequently dirty. If you have run /ultrareview on any of them recently, treat those keys as having left the machine and rotate them once. Then upgrade before the next review run.
Changelog — 2.1.248
New 2.1.248

--restricted gives you a Claude Code that cannot run code

The new --restricted flag (or CLAUDE_CODE_RESTRICTED=1) removes the built-in tools that run commands or code and removes WebFetch unless it is named in --tools. It keeps the file tools inside the working directory, refuses bypassPermissions, and ignores your user, project, and local settings files.

That last clause is the one people will trip over. A restricted run deliberately ignores your settings.json allowlists, so nothing you have permitted elsewhere carries into it.

So what for TSD: This is the mode for any run whose input you did not write — parsing a client's inbox, chewing on scraped review text, processing form submissions. It is also a concrete answer when an SMB client asks what your agent can do inside their repo: read files in one directory, no shell, no outbound fetch, and no way to escalate.

◆ Token cost and context budget

Fix 2.1.248

Long sessions lost their prompt cache about once an hour

Tool definitions were being re-rendered after an OAuth token refresh, which caused a full prompt-cache miss roughly once an hour in long sessions and lost the extended-thinking context along with it. A second, related fix covers the ScheduleWakeup tool definition changing between a session and its --resume when the account had entered usage overage, which blew the cache on the resumed session's first turn.

So what for TSD: This was a silent tax on every multi-hour build session and every scheduled loop you run, and there is nothing to configure — upgrading collects the savings. If you have been reading cost numbers off long client sessions to decide anything, re-baseline after the upgrade before you act on them.
Changelog — 2.1.248
Improve 2.1.248

The Workflow tool's description shrank from 5.7k tokens to about 1k

The script-writing reference moved out of the tool description and into a bundled workflow-authoring skill, cutting the tool's prompt footprint by roughly 4.7k tokens.

That budget comes back in every session that has the Workflow tool available, whether or not you ever call it.

So what for TSD: Free context on every run, no action needed. The tradeoff is that workflow-authoring guidance now loads on demand, so when you next write a workflow script expect the model to pull that skill in first rather than knowing the API cold.
Changelog — 2.1.248
Feature 2.1.248

experimental.cacheTtl sets a cache window per agent

Agent frontmatter now accepts experimental.cacheTtl with a value of "5m" or "1h". It applies as that agent's prompt cache TTL when no subagent TTL setting is configured.

So what for TSD: Put "1h" on the agents behind your slow scheduled jobs — this changelog scout, the loose-ends steward — where a wakeup can land far apart. Leave short-lived one-shot subagents alone. The point is that it is per-agent now, so you no longer pick one TTL and live with it everywhere.

◆ Unattended runs stop failing quietly

Fix 2.1.248

A backgrounded worktree session could lose its own checkout

Background sessions running in a git worktree now hold that worktree's lock while they run, so cleanup routines and git worktree remove leave the directory alone. Previously the checkout could be pulled out from under a running session.

So what for TSD: This is the exact failure your loop-engineering pattern is built to hit — isolated worktrees, background agents, a cleanup pass at the end. If a nightly loop has stopped producing output without an error you could find, upgrade and re-run it before you go digging through your own code.
Changelog — 2.1.248
Fix 2.1.248

Hooks that emit bad JSON now report a real error

A hook printing a stdout {…} object that is not valid JSON was silently treated as plain text; it is now reported as a hook error carrying the parse message. Separately, background sessions that used to wait silently when a PermissionRequest or PreToolUse hook printed an invalid answer now name the hook and the schema error in the claude agents row.

So what for TSD: Both of these turn a hung unattended run into a legible one. If you have hooks gating permissions on any scheduled job, this is the difference between a job that mysteriously stalls overnight and a row that tells you which hook broke.
Changelog — 2.1.248
Change 2.1.248

/loop's self-paced and autonomous modes are now always available

Self-paced dynamic mode and the no-prompt autonomous default are no longer gated, including on Bedrock, Vertex, and Foundry. Cross-session messaging (SendMessage / ListAgents) between sessions on the same machine picked up the same treatment, and now also works when telemetry is disabled.

So what for TSD: Minor for you today since you run on the first-party API where these already worked. Worth knowing if you ever stand up a client-hosted deployment on Bedrock or Vertex, because the loop and multi-session patterns you rely on will now port there unchanged.
