◆ Opus 5.5 lands as the default — and the default plan model flips with it

New 2.1.280

Claude Opus 5.5 (claude-opus-5-5) is now the default Opus model

1M context window, $4 per Mtok input / $20 per Mtok output, $0.20 per Mtok for cache reads. It replaces the prior Opus default across Claude Code.

So what for TSD: This is a capability bump for the hard problems — long-context Next.js/Supabase debugging, multi-file refactors on client codebases. Run /model to see what you're actually on before a big session, and keep the cache-read discount in mind: it's a fraction of the input rate, so structuring long sessions to reuse context still pays off.
Claude Code Changelog — 2.1.280
Behavior change 2.1.280

Default model on Pro and Team Standard plans changes from Sonnet to Opus

New sessions on those plans now default to Opus instead of Sonnet. Paired with the Opus 5.5 launch, this means the out-of-the-box experience just got more expensive per token — and, for anyone metering usage against a plan cap, will burn through it faster.

So what for TSD: Check which plan the TSD account is on and confirm what a fresh session opens with. If routine work — quick edits, this daily scout job, small client tickets — doesn't need Opus-level reasoning, pin Sonnet explicitly for those sessions rather than letting the new default eat into usage that Opus-tier work actually needs.

◆ Headless and background-agent reliability — the bugs that bite scheduled jobs

Fix 2.1.280

Messages sent to a background subagent were silently lost in headless and SDK sessions

No error, no retry — a message sent to a running background subagent in a headless or SDK-driven session just disappeared. A related fix stops a finished subagent's report from being lost when the launching conversation gets compacted.

So what for TSD: This is exactly the failure class that matters for a job like this scout run — unattended, headless, no human watching for a dropped message. If a scheduled job's subagent step ever produced no output with no visible error, this bug is a plausible cause. Worth a mental note, not an action: nothing to change, just don't rule out silent message loss as an explanation for a past no-op run.
Claude Code Changelog — 2.1.280
Fix 2.1.280

Auto mode stops looping when a safety check stalls

Two related bugs: auto mode would retry an action over and over when a safety check declined to review it, and would deny actions over and over with no pause when a safety check gave no answer at all. Both are fixed.

So what for TSD: If any Nash OS automation runs in auto mode with safety checks enabled, this closes a spin-loop failure mode that would have burned tokens or stalled a run indefinitely without surfacing as a clean error. No config change needed, just fewer mystery hangs going forward.
Claude Code Changelog — 2.1.280
Fix 2.1.280

Background shell tasks no longer flag benign non-zero exits as failures

A background shell command that exits non-zero for a non-error reason — a lint warning threshold, a tool that uses exit codes as status flags — was being reported as a failed task.

So what for TSD: Relevant if a scheduled job shells out to build/deploy tooling that uses non-zero exits as anything other than "it broke." Fewer false-failure alerts from background steps going forward.
Claude Code Changelog — 2.1.280

◆ /ultrareview — two straightforward fixes

Fix 2.1.280

Stopped cloud reviews no longer misreport as completed or as a retryable error

A stopped /ultrareview cloud review used to show as finished, or as an error worth retrying, instead of showing as stopped. A separate improvement keeps renamed copies of key files on your machine during upload instead of sending them.

So what for TSD: If a review run was ever cancelled mid-flight, trust the status less before this fix — a "completed" or "retry" label could have been wrong. Going forward the status should be accurate, so no workaround needed.
