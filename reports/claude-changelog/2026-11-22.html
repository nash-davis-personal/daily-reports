◆ Your automations

Breaking 2.1.325 / 2.1.329

Scheduled tasks can hang on a prompt or need scheduling again

Since 2.1.325, scheduled tasks and /loop ask before running a skill that declares allowed-tools or hooks. Adding Skill(name) to permissions.allow lets it run unattended. The same release narrowed "Always allow" in Desktop, IDE and SDK hosts, and the notes warn that a task relying on one of those rules can now wait for you.

2.1.329 adds a second catch: in new signed-in sessions, most scheduled tasks saved by earlier versions need scheduling again. Using --resume on their own session still runs them.

So what for TSD: Of your personal skills, only nano-banana declares tools or hooks, and your settings have no Skill() rules. Add Skill(nano-banana) if a scheduled task calls it. After updating, compare the Nash OS Machine page against all 28 tasks and reschedule anything that stops logging.
Changelog: 2.1.325 and 2.1.329
Improved 2.1.329 / 2.1.330

Recurring tasks last 30 days and show up in /tasks

Recurring scheduled tasks and /loop now run up to 30 days while their session stays open, and they say when they end. Tasks made before 2.1.330 still end at 7 days. /tasks now lists the session's scheduled tasks, /loop wakeups, goal and forks, and x stops one after asking.

So what for TSD: Recreate any session-based /loop you want running through a client launch so it picks up the 30-day limit. Use /tasks as the quick check for what a long session still has running.
Changelog: 2.1.329 and 2.1.330
Breaking 2.1.325 to 2.1.330

More commands ask first, and where nobody can answer they are refused

Sandboxed Bash now follows the normal permission flow unless you set sandbox.autoAllowBashIfSandboxed: true. Auto mode ignores more allow rules that run any package, such as Bash(pnpm dlx *), and leaves those calls to its safety check. Sandboxed commands lose write access to some sensitive home folders. More rm commands aimed at the root, home, a top-level folder or the working folder now need approval.

Hooks also changed. A hook's "decision": "block" holds in more cases, so a hook that always prints one may start blocking calls.

So what for TSD: Unattended jobs that lean on pnpm dlx wildcards or broad rm can be refused after you update. Replace wildcard rules with exact commands for the jobs that matter, starting with the ones that push client sites.
Changelog: 2.1.325, 2.1.326, 2.1.327 and 2.1.330

◆ Build quality and speed

Improved 2.1.328 / 2.1.329

/code-review reports bugs, ranks them, and covers the whole branch

On most models, /code-review now reports only bugs and CLAUDE.md violations, and /simplify handles reuse and efficiency cleanups. Findings are marked Important, Pre-existing or Nit, and each summary ends with a suggested fix. With no target, it reviews the whole branch against the default branch, and a bug that lost the diff on multi-commit branches is fixed.

So what for TSD: Run /code-review once before each client merge on Bisque, Studio C and Sonderwerks, and clear every Important finding. Pre-existing findings make a ready-made list for a paid cleanup conversation.
Changelog: 2.1.328 and 2.1.329
Feature 2.1.326 to 2.1.330

Code Mode got faster and works with agent teams, with one hook change to watch

Code Mode now runs alongside agent teams, drops a 0.75 second pause after most scripts in auto and bypass modes, uses shorter tool descriptions, and caches prompts better when MCP servers are attached. It also runs dev servers as background tasks.

One safety change matters: a PreToolUse hook that errors no longer refuses a script's tool call. A hook that must block needs "onFailure": "block".

So what for TSD: Try Code Mode on one multi-file Next.js job and compare tokens and time. Before using it near production, add "onFailure": "block" to any hook that guards deploys, including the Vercel scope guard if it runs as a hook.
Changelog: 2.1.326, 2.1.328 and 2.1.329

◆ Phone and worktrees

Fix 2.1.326 to 2.1.330

Worktrees stop losing files, and Remote Control streams replies to your phone

2.1.327 fixes Remote Control deleting a running session's git-ignored files, such as .env, when its server stopped in worktree mode. ExitWorktree now asks before removing a worktree that may hold unsaved work, and 2.1.330 stops it deleting one another running session is using. Since 2.1.326, replies from claude remote-control, Desktop and VS Code sessions stream to your phone or browser as they are written.

So what for TSD: Until you update, keep client .env files recoverable from Vercel or Supabase and avoid stopping a Remote Control server in worktree mode while a session runs.
