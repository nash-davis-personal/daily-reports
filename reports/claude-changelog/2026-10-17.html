◆ Subagents and unattended runs

Changed 2.1.302

Fork subagents ship on by default in headless, SDK, desktop and VS Code sessions

Fork subagents (subagent_type: "fork") were already on in the terminal. As of 2.1.302 they are also on by default in claude -p, the Agent SDK, the desktop app and VS Code. Set CLAUDE_CODE_FORK_SUBAGENT=0 to turn them off. claude mcp serve never offers them.

In the same release, the desktop app and VS Code always run the main conversation's subagents in the background, matching the terminal. A subagent that itself calls Agent in claude -p, the SDK, the desktop app or VS Code now runs that call in the foreground by default.

So what for TSD: Your scheduled desktop tasks (this scout included) and any SDK-driven client automations just gained a new subagent type with no config change. A fork starts from the parent conversation, so expect each spawn to carry more context than a fresh agent. Watch token usage on the next few daily runs, and if a routine starts forking where a clean Explore agent would do, pin it off with the env var in that task's environment.
Changelog, 2.1.302 changed
Fix 2.1.302

Cloud routines: no more duplicate reruns, honest status, and a reason when a run never starts

Four routine changes landed together. A scheduled routine run that failed partway could be run again from the start an hour or more later, which the changelog says "could repeat work such as posting the same report twice"; that is fixed. Runs whose cloud session stopped unexpectedly no longer show as Completed, and runs archived before they started no longer show as Cancelled; both now show as failed. A routine's page also gets a banner explaining why its last run didn't start, such as hitting the organization's concurrent cloud session limit.

So what for TSD: These apply to cloud routines. Your daily-reports scouts run as local desktop scheduled tasks, so they were not exposed to the double-post bug. If you have moved or plan to move any client-facing job (a Bisque inventory digest, a Studio C reminder sender) to a cloud routine, this was the bug that would have sent a client the same message twice. It is now safe to rely on the run status shown on the routine page.

Changed 2.1.302

Headless runs on third-party providers now start in default permission mode

claude -p and Agent SDK sessions with no permission mode set now start in default mode on third-party providers when telemetry is off or on a fresh install. Passing --permission-mode auto keeps auto.

So what for TSD: This only bites if a job runs through Bedrock or Vertex. If you ever wire a client's automation to their own cloud provider account, set --permission-mode explicitly in the invocation so a fresh install doesn't stall on a permission prompt nobody is there to answer.

◆ Deadlines and settings

Notice 2.1.302

Standalone Claude Design closes December 14, 2026

/design-sync and /design-login now show a notice that standalone Claude Design at claude.ai/design closes by December 14, 2026. The changelog does not say what replaces it.

So what for TSD: If any client mockup, brand board or handoff lives only in claude.ai/design, export or sync it into the repo (or Vercel via the design import) before December 14. Don't promise a client a design workflow built on the standalone site past that date.
Changelog, 2.1.302 added
Added 2.1.302

Idle compaction toggle, and more control over auto mode's classifier

/config gains an Idle compaction row to turn idle compaction off or back on, and the notice after an idle compaction now says how to disable it. CLAUDE_CODE_AUTO_MODE_MODEL picks the model for the client-side auto mode classifier; it does not affect server-side auto mode. Separately, with the server-side classifier, a conversation too long for the safety check is now compacted instead of every checked tool call being denied.

So what for TSD: If you leave a long client build session open over lunch and come back to a compacted context you didn't want, turn idle compaction off for that project. The auto mode compaction fix matters more: long autonomous sessions on big repos could previously hit a wall where every tool call got refused.

◆ MCP, plugins and hooks

Fix 2.1.302

MCP servers on protocol 2026-07-28 stop showing zero tools

Servers that negotiated protocol version 2026-07-28 but omitted resultType, ttlMs or cacheScope could show no tools, or fail every call. Fixed. Also in this release: plugin command and agent files load with far fewer file system calls at startup, and prompt and agent hooks now run at most 12 of one event at a time while the rest queue.

So what for TSD: If one of your connectors (tsd-portal, nash-os, a client server) has recently shown up empty after a server update, upgrade before debugging the server. If you build an MCP server for a client on the newer protocol, still send those fields so older clients behave.
