◆ Today's release, both lines of it

Fix 2.1.237

Gateway and custom base URL sessions were not caching the prompt

The entry reads "Fixed prompt caching for sessions using an LLM gateway or custom base URL." Prompt caching is the thing that keeps a long session affordable. Without it, every turn re-pays full input price for the entire conversation prefix, and the cost curve of a long build session goes from flat to linear.

This only bites sessions pointed at something other than the direct Anthropic API. If your terminal sessions all hit the API directly, you were never affected and nothing changes for you.

So what for TSD: Check whether anything you run sets ANTHROPIC_BASE_URL or routes Claude Code through a gateway, including the scheduled tasks and any Vercel AI Gateway wiring. If yes, update before your next long session and stop paying the uncached rate. If no, this release is a one-line read and you can move on.

New 2.1.237

A built-in "Concise" output style

Claude leads with results and skips preamble and narration, while doing the work just as thoroughly. It is selected under Output style in /config, so it applies at the session level with no prompt engineering and no CLAUDE.md instruction to maintain.

You have been enforcing roughly this rule by hand for months through global instructions. A built-in style is more durable than a memory file, because it does not compete for attention with everything else in context.

So what for TSD: Turn it on and see whether it lets you delete some of the voice rules you carry in ~/.claude/CLAUDE.md. Shorter global instructions mean more room for actual project context on Bisque and Sonderwerks work. Keep the rules that are specific to your writing voice, since this style governs how Claude reports work rather than how it drafts client copy.

◆ Running more than one session at a time

New 2.1.236

notify_when_idle on cross-session SendMessage

One session can now ask another Claude Code session on the same machine to send a single notice when it next goes idle. The changelog is explicit that it is opt-in, one-shot, and involves no polling, and that it works on macOS and Linux.

Until now, a coordinating session that wanted to know when a worker finished had to guess an interval and keep checking. That burned tokens on every check and still landed late. A one-shot idle notice replaces the whole pattern with a single call.

So what for TSD: This is the piece your loop designs kept working around. Anywhere a steward session is currently sleeping on a timer waiting for a delivery session to finish, replace the timer with an idle notice. Fewer wake-ups, no wasted polling turns, and the handoff fires the moment the worker is actually done.
Claude Code changelog — 2.1.236
Improve 2.1.236

SendMessage now refuses a burst up front instead of reporting phantom sends

Once a rapid burst would exceed what the recipient session's inbox accepts, further messages are refused immediately. Previously they were reported as sent and then dropped.

Silent drops are the worst failure mode in a multi-session setup, because the sender believes the handoff happened and moves on. Two related fixes landed alongside it: SendMessage calls were being rejected when a malformed closing tag left the message text inside the summary field, and Remote Control now marks a session offline within seconds of the CLI exiting rather than leaving a dead session looking live.

So what for TSD: If you have ever had a fleet run where one agent's instructions never arrived and you could not reproduce it, this is a plausible cause. Worth a re-run of any orchestration you shelved as flaky before you rewrite it.
Claude Code changelog — 2.1.236
Fix 2.1.236

Removing a directory a session had switched into broke four separate things

Clipboard copy, background housekeeping, background sessions and local MCP logs all broke after the removal. The regression dates to 2.1.229. A companion fix covers skills hot-reload in SDK and VS Code sessions, which had been raising an error on every skills change once the session's working directory was deleted.

The failure profile here is specific: it needs a session that changed directory into a path that later disappears. Worktree-based workflows produce exactly that shape, since the worktree is created, worked in, and then cleaned up.

So what for TSD: Your isolated-worktree agent runs are the case this describes. If background agents have been going quiet or MCP logs have been empty after a worktree cleanup, update rather than debugging your own harness.

◆ Defaults, sandboxing, and what auto mode could be fooled by

New 2.1.236

ANTHROPIC_DEFAULT_MODEL sets a starting point rather than a pin

It sets the model new sessions start on. A /model pick still overrides it and persists across restarts, which the changelog notes is a departure from how ANTHROPIC_MODEL behaves.

That distinction is the whole point. ANTHROPIC_MODEL forces a model and keeps forcing it, so a mid-session switch does not survive. A default is a starting position you can move off and stay moved off.

So what for TSD: Useful for the unattended work. Set a default model for scheduled tasks and cron-driven runs so an interactive experiment does not leak a model choice into tomorrow's automated run, and keep manual sessions free to switch without fighting the environment.
Claude Code changelog — 2.1.236
Improve 2.1.236

Sandbox wildcard deny rules now win inside allowed read regions on macOS

Three changes in one entry: a wildcard read-deny such as **/.env now takes precedence inside allowed read regions, it covers the contents of matched directories, and it cannot be bypassed by renaming the denied file.

Read that as an admission that the deny rule was previously losing to a broader allow rule in the same config. Anyone who wrote a deny rule for secrets and assumed it held may not have had the protection they configured.

So what for TSD: You keep client Supabase service keys and Vercel tokens in .env files across Bisque, Studio C and Sonderwerks repos. If you have sandbox deny rules configured, they behave the way you intended only after this update. Update, then re-read your rules once to confirm they say what you think they say.
Claude Code changelog — 2.1.236
Improve 2.1.236

Auto mode's clean-tree check could be fooled by a git config setting

A repo with status.showUntrackedFiles=no was making auto mode's git status check report a clean tree. Two more auto mode changes landed with it: Monitor allow rules are now set aside while auto mode is active so Monitor commands get reviewed the same way Bash commands are, and the classifier on Bedrock, Vertex AI, Foundry, and in sessions with telemetry disabled now uses the same defaults as on the Claude API, including severity-scored classification.

The pattern across all three is auto mode being less trusting of its own shortcuts. A false clean-tree reading is the one with teeth, because a clean tree is the signal that says destructive operations are cheap to undo.

So what for TSD: Worth checking whether any client repo carries that git setting before you run auto mode in it. Also note the classifier parity item if you ever point a session at Bedrock or Vertex for a client with cloud-vendor constraints, since those sessions were previously running with weaker defaults than your direct-API sessions.
Claude Code changelog — 2.1.236
Improve 2.1.236

Slash-command typos no longer run the closest fuzzy match

Pressing Enter on a slash-command typo, or on a command unavailable in the current session, now reports the problem instead of running whatever the fuzzy matcher liked best. Prefixes and aliases still run as before.

So what for TSD: Small, and it removes a real hazard. You carry a long list of custom commands with overlapping names, and a mistyped one silently running a different command is the kind of thing you only notice after it has already done something.
