◆ Plugins and MCP

New 2.1.287

Claude Mods: plugins that change deeper behavior, plus a built-in watcher agent

The changelog adds Claude Mods with one line of description: plugins may now modify deeper behavior. It does not say which behaviors are open to mods, so treat the scope as unknown until the docs fill in.

The first built-in mod is called You should know. A side agent watches the session and flags things you or Claude might miss. Turn it on with /plugin enable cc-plugin-you-should-know@builtin. The changelog limits it to first-party sessions with telemetry on.

So what for TSD: Enable You should know on one real client session this week (a Bisque or Studio C change with a deploy at the end) and see whether its flags catch anything your verify skill and the skeptic step in your loops miss. If it only repeats them, turn it off. Hold off on writing your own mod until the docs say what a mod can touch.
Changelog 2.1.287
Changed 2.1.287

alwaysLoad: false now defers every tool on that MCP server

Setting alwaysLoad: false on an MCP server now puts all of that server's tools behind tool search. Related changes in the same release: large MCP tool results use less memory and produce smaller session files, and Claude is no longer told to page a large JSON result with Read's offset and limit, which cannot split one long line.

So what for TSD: Your sessions carry a long tail of MCP servers that most runs never call (Canva, Calendly, Higgsfield, Notion, Vapi). Set alwaysLoad: false on each of those in the MCP config so their tool definitions stay out of context until a task asks for them. Leave it off for the servers a scheduled job calls on every run.
Changelog 2.1.287
Feature 2.1.287

MCP servers can send URL prompts, and some servers may stop connecting

Claude Code now supports URL prompts from MCP servers on the 2025-11-25 protocol, for example to sign in. The changelog ships the workaround in the same line: if a server no longer connects after this update, add "bareElicitationCapability": true to its MCP config entry.

So what for TSD: After updating, run /mcp on both Macs and compare against what connected before. For any server that newly fails, add the bareElicitationCapability line to its entry first, before spending time on auth or network debugging. Check the ones your launchd jobs depend on (supabase, nash-os, tsd-portal) before the next unattended run.

◆ Permissions and safety

Changed 2.1.287

Three shell-write paths now stop and wait for a person

First, a shell write through a repo-committed symlink onto a sensitive file, or out of the working tree, now names where it lands and waits for a person. This applies to lines with a ~ target too.

Second, whole-tool Bash allow rules and allowing hooks now prompt for shell writes to files that Claude Code's file tools refuse outright. The changelog names the Anthropic profile store and the host credentials file.

Third, a fix: a dangerous rm, such as one on / or the home directory, lost its always-ask safeguard when the same command also redirected output to a ~ or wildcard path. The safeguard holds now.

So what for TSD: The rm fix is the reason to update today on any Mac that runs loops with a broad Bash allow rule. The other two changes can stall an unattended job that writes through a symlink or touches a credentials file, because nobody is there to answer the prompt. Scan the last few launchd run logs after updating for a job that hangs on a permission prompt, and move any such write into a script outside the agent.

◆ Unattended runs and background agents

Fix 2.1.287

Headless MCP: fewer false auth flags, faster startup, no double calls

Headless sessions no longer report an MCP server as needing authentication after one refused call when later calls succeed. A remote server whose first connect fails transiently is now retried without waiting for the slowest server to finish connecting. An MCP connector tool call could occasionally run twice, or the connector's calls could fail until restart, when its server changed which protocol version it supports. That is fixed.

Two more for scripted runs: claude -p and SDK sessions no longer repeat a model fallback on every later message after a mid-reply model switch, and a hook configured with asyncRewake whose script file is missing is now reported once instead of waking Claude over and over.

So what for TSD: The double-run fix matters most for jobs that write through a connector (CRM dispositions, Notion pages, calendar events), since a repeated call there creates a duplicate record. Update the Macs that run the scheduled tasks, then check the next morning's runs for duplicates that used to appear and for "requires authentication" lines that no longer do.
Changelog 2.1.287
Changed 2.1.287

claude agents: queued replies, a name filter, and prompts in order

Replies sent from claude agents now arrive as queued messages. Slash commands other than /stop sent while a turn is running now run when the turn ends. The agents view gains an n:<text> filter that matches session names and tasks, and Enter opens the first match.

Waiting permission prompts now show oldest first, so a new prompt no longer covers the one you are reading. Two fixes ride along: claude agents sometimes hid the permission prompt a background session was waiting on, and a background session could not be reopened after its agent exited and removed the worktree it started in.

So what for TSD: If you steer background agents mid-turn, expect your message to land after the current step finishes. Use /stop when you need to interrupt. With several client sessions running, name them by client (bisque, studio-c, sonderwerks) so n:bisque pulls the right one in one keystroke.
Changelog 2.1.287
Changed 2.1.287

1M context is the default on Bedrock, Vertex, Foundry and the apps gateway

Opus 4.7 and later, plus Fable, now use a 1M context window by default on Bedrock, Vertex, Foundry and the Claude apps gateway, with no [1m] suffix. Setting CLAUDE_CODE_DISABLE_1M_CONTEXT=1 keeps 200K.

So what for TSD: This only touches you if a client deployment routes Claude Code through one of those four providers. If you ever set one up for a client on their own cloud account, a larger default window means larger possible bills per session, so decide on the 200K env var at setup time.
