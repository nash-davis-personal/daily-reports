◆ Automation reliability

Fix 2.1.288

Unattended sessions recover from stalled streams instead of dying

A cluster of related fixes: mid-response API timeouts in non-interactive sessions and subagents now continue from the partial response instead of failing the whole turn, and thinking-only responses retry instead of erroring out. Long conversations that previously failed with "Prompt is too long" now auto-compact instead. The unattended retry watchdog (CLAUDE_CODE_RETRY_WATCHDOG) used to retry for hours after a very long response stream failed; it now re-streams and gives up after three timeouts. Auto mode also now compacts a conversation that's grown too long for the safety classifier, instead of prompting for or failing every tool call.

So what for TSD: This is the exact failure mode that would quietly break a cron-triggered agent job — a stalled stream or an oversized context used to mean a hung or dead run with no output. If you're running (or planning to run) anything unattended against client repos — scheduled scans, batch content generation, nightly builds — this release is less babysitting and more actual delivery per run.

Fix 2.1.288

CLAUDE.md and .claude/rules load on Write and Edit, not only Read

Path-scoped .claude/rules and nested CLAUDE.md files were only loading when a Read tool call touched a file in their scope. If Claude created or changed a file in that scope without reading it first, the applicable rules never loaded.

So what for TSD: If you keep per-folder CLAUDE.md conventions in any client repo (Bisque, Studio C, Sonderwerks) — say, a rules file scoped to an API routes folder or a Supabase migrations directory — and Claude ever wrote a new file there before reading an existing one, those rules were silently skipped. Worth a spot-check on any repo where you lean on nested rules rather than one root CLAUDE.md.
Changelog: 2.1.288
Fix 2.1.288

Plugin-defined agents spawned by name now use their own config

In agent teams, a plugin-defined agent spawned by name was running with Claude Code's default prompt, tools, disallowedTools and effort instead of the settings the plugin actually configured for it.

So what for TSD: If you've built or plan to build reusable subagents for repeatable client work (a content-reviewer agent, a migration-runner agent) and ship them as a plugin, they'll now actually run with the tool access and effort level you set — not a generic fallback.

◆ Code review & guardrails

Feature 2.1.288

/code-review gets a findings dial: --max-findings <n>|all

Pass --max-findings <n> or --max-findings all to report more or fewer findings than the usual cap. The choice sticks until you run --max-findings default.

So what for TSD: Tune review noise per job — a quick landing-page tweak doesn't need the same finding count as a Supabase schema migration. Useful if you've ever felt a review was cut short on a bigger diff, or too noisy on a small one.
Changelog: 2.1.288
Fix 2.1.288

Dangerous rm inside bash -c/sh -c can no longer skip the safety prompt

A destructive rm (one targeting / or a home directory) nested inside a bash -c or sh -c script was running without approval under bypassPermissions mode or a shell allow rule — the always-ask safeguard didn't catch it there.

So what for TSD: A concrete, citable example if a client asks how you keep AI-assisted dev from going rogue on their machine or CI. Worth knowing the gap existed if you run with broad bash allow rules or bypassPermissions on any client-facing automation.
Changelog: 2.1.288
Improve 2.1.288

Background command time limit now only applies to unattended sessions

The background command time limit now applies only in unattended sessions (-p, Agent SDK, CI, cloud). Terminal, desktop app and VS Code sessions have no limit.

So what for TSD: Long-running local dev servers, watch builds or indexing jobs kicked off from an interactive session won't get killed by a timer anymore — that limit is now reserved for scripted/CI runs where it actually belongs.
