Your sessions can now message each other, and the 200-subagent cap is gone.

2.1.224 is the biggest release since Opus 5 landed two weeks ago, and the theme is agents that coordinate. Claude Code sessions can now send messages to each other across all of your machines, discover each other with ListAgents, and spawn subagents without hitting the old 200-per-session ceiling. ◆ Sessions that coordinate with each other

New 2.1.224

Cross-session SendMessage, with ListAgents to find the other sessions

Claude Code sessions can now message each other, including sessions running on a different machine of yours, and ListAgents enumerates what is out there to talk to. The changelog scopes this to macOS and Linux.

This is a different primitive from spawning a subagent. A subagent is a child you own for the length of a task. This is one long-lived session handing something to another long-lived session that already has its own context loaded.

So what for TSD: The obvious first use is your scheduled work. A vault-refresh session that already holds the wiki in context can be pinged by the loose-ends steward instead of each one rebuilding the same context from cold. Start with one pair before you wire a mesh — a message to a session running with bypassed permissions is a real blast-radius question, which is why the setting below exists.
Changelog · 2.1.224
New 2.1.224

crossSessionInbound and dialogExpiry gate what arrives

Messages sent to a session that is running with bypassed permissions are held for your approval. Messages to other sessions auto-deliver. A related fix: SendMessage used to report "Message sent" when the write to a teammate's inbox had actually failed, and failed deliveries are now reported as errors.

So what for TSD: The false-success fix matters more than the feature for you today. Any automation that fired a SendMessage and treated the confirmation as proof of delivery was capable of lying to you. If you have a loop whose handoff step reports success without a downstream check, that check is still worth adding.
Changelog · 2.1.224
Improve 2.1.224

The 200-subagent-per-session spawn cap is gone

Long-running sessions no longer refuse new agents once they have spawned 200 over the session's lifetime. Concurrency limits (default 20, via CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS) and spawn depth (default 3) are unchanged.

Worth reading alongside the workflow tooling's own 1000-agent lifetime backstop, which is set far above any real workflow and is not affected here.

So what for TSD: This unblocks the long unattended session, which is exactly the shape your loops take. A steward that runs for hours over a client repo and fans out per file was the case that hit 200 and started refusing work partway through, with no obvious symptom other than agents that stopped spawning.

◆ Secrets, the sandbox, and what leaves your machine

Fix 2.1.224

Sandbox deny entries written with a trailing slash were silently bypassable

A filesystem deny entry written as denyRead: "~/.aws/" could be bypassed on both Linux and macOS. The trailing slash defeated the match. Separately, sandbox violation details never appeared in Bash tool results, so Claude could not see which file or network access was denied or why, and would retry blind.

So what for TSD: Go look at your sandbox settings right now and check every denyRead and denyWrite for a trailing slash. If you wrote one that way, it has not been protecting that path. Anything covering ~/.aws, ~/.config/vercel, or a Supabase service-role key file is the one to check first.
Changelog · 2.1.224
Behavior change 2.1.224

Sharing a feedback transcript now uploads your system prompt, which contains your CLAUDE.md

With your consent, the feedback survey's transcript share now also uploads the last request's model settings: the system prompt (which includes your CLAUDE.md instructions), tool definitions, and model parameters. Secrets are redacted as before, and these fields are dropped first if the share is too large. A companion fix stops long-session shares from failing silently and showing a success message.

So what for TSD: Your global CLAUDE.md names clients, deploy scopes, vault paths, and the Bisque Vercel arrangement. None of that is a secret a redactor would catch, because it is prose. Consent is still per-share and this only fires when you actively submit feedback, so the rule is simply to read the consent line before clicking through on a session that was doing client work.
Changelog · 2.1.224
New 2.1.224

Sandbox credential masking gets structured extraction, JWT awareness, and AWS SigV4 re-signing

New options: extract and onExtractNoMatch for pulling a credential out of a structured env value, decode: "jwt" with maskClaims for JWT-aware masking, and awsPairs/sigv4 for re-signing AWS SigV4 requests at the proxy. All of these require network.tlsTerminate and are honored only from user, managed, or --settings settings.

The scope restriction is the important half: a repo-local .claude/settings.json cannot turn these on, so a client repo cannot define its own masking rules.

So what for TSD: decode: "jwt" with maskClaims is the one that maps to your stack. Supabase anon and service-role keys are JWTs, so a sandboxed command can now hold a structurally valid token while the real claims are substituted on egress. That is the difference between running an agent against a client's Supabase project and not.

◆ Session integrity

Fix 2.1.224

Project paths over 200 characters resolved into another project's session directory

Long project paths were being sanitized to a shared prefix, so two different projects could land on the same session directory. Session list, rename, fork, delete and /resume all crossed projects as a result. Deleting a session in one project could remove one belonging to another.

So what for TSD: Check whether any client checkout sits at a path over 200 characters. Deeply nested worktrees under a long parent are the realistic way to get there, and the failure mode is a /resume that hands you the wrong client's session. Cheap to verify: pwd | wc -c in each project root.
Changelog · 2.1.224
Fix 2.1.224

A recreated Remote Control session uploaded prior local conversation history into the new session

When a Remote Control session was recreated after its server session expired, it pushed the earlier local conversation history into the fresh session. Related: Remote Control now archives the stale server session instead of leaving a dead one listed after compaction or /resume, and a plugin's install records were being silently corrupted when the same plugin is installed across multiple projects.

So what for TSD: Same class of problem as the path collision — context arriving somewhere it was not supposed to go. If you use Remote Control to check on a running build from your phone while switching between client sessions, this one was capable of carrying one client's conversation into another session's history.

◆ Self-hosted runners, plugins, and Remote Control polish

New 2.1.224

claude self-hosted-runner turns your own machines into session hosts

Self-hosted environments let Claude Code web, mobile, and desktop sessions run on your own machines or containers. The changelog gates this to Team and Enterprise plans.

So what for TSD: Plan-gated, so it is off the table today unless you move TSD onto Team. File it as a sales fact instead of a tool: when a client asks whether agent work touches infrastructure they do not control, "it can run on hardware you own" is now a true answer with a plan attached to it.
Changelog · 2.1.224
New 2.1.224

archive plugin source: install from a zip over HTTPS with SHA-256 pinning

Plugins can now be installed from a zip served over HTTPS, with no git or npm in the path, and with optional SHA-256 pinning of the archive.

So what for TSD: This is a distribution channel for your own skills. Dropping a zip on a Vercel-hosted URL with a pinned hash is a simpler handoff than granting repo access, which matters the day you package something like the vault or sales skills for someone outside your machines. Pin the hash if you ever do.
Changelog · 2.1.224
Improve 2.1.224

Remote Control stops going quiet on you

Attached web and mobile clients now see compaction progress and the post-compaction boundary instead of a silent pause, and /clear resets propagate to attached clients. Connection failures show a persistent failure indicator with details and a reconnect shortcut in place of an 8-second toast. Auto-start no longer intermittently fails with "Remote credentials fetch failed" on a cold start with a stale login token.

Two more on the same surface: a resumed session was silently reconnecting Remote Control after you turned it off, and the VS Code extension showed it as connected after the connection had failed.

So what for TSD: The silent-reconnect-on-resume fix is the one to note. If you turned Remote Control off deliberately on a session and later resumed it, it was coming back on without telling you. Everything else here makes phone-checking a long build actually readable.
